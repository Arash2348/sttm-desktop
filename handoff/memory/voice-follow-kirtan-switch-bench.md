**Baseline finding (first 10 min, shipped constants SMIN 0.65/MARG 0.15/CONFIRM 2):** switch recall 10/12 (83%) — recall is FINE — but **22 false switches** and initial-lock spuriously hit NB5 before correcting to MNB. This is the FP frontier [[voice-follow-realkirtan-frontier]] made concrete: the gate that gives 0 FP on 3 clean studio shabads gives ~2 FP/min on a 90-shabad real-kirtan field. Root cause: with 90 shabads × short line sets, partialRatio almost always finds a spurious ≥0.65 substring match (cand often 1.00 on 1-line segments); flip-flops (A->B->A within 2s) show CONFIRM=2 (=1s at hop 0.5) is too weak. Initial-lock number here is a rough proxy — the real app locks via first-letter banidb search, not maxLineScore over a fixed set.

**Sweep outcome (2026-09-10):** CONFIRM is the ONLY lever that moved the curve. DWELL (min-dwell cooldown) and OPEN_LINES (candidate scored vs opening lines only) had ZERO effect (false contenders are short 1-line shabads where opening==all; dwell just delays commits without preventing the excursion).

**METRIC-VALIDITY CORRECTION (2026-09-10, supersedes the count-based CONF=4 pick):** false-switch COUNT is an artifact — a suppressed 0.5s excursion counts the same as a suppressed 20s one. Added a UX metric to the harness: integrate believed-shabad vs playing-shabad over time (STEP 0.2s), splitting "wrong" into **STALE** (still showing the PREVIOUS shabad = graceful late switch, tolerable) vs **ERRONEOUS** (unrelated shabad = jarring jump, the thing to avoid). Full 86-min under this metric:
- CONF=2: on-correct 68.3% / stale 11.0% / **erroneous 20.6%** / 159 FP / lat 8.0s
- **CONF=3: on-correct 68.9% / stale 17.8% / erroneous 13.2% / 52 FP / lat 9.8s ← KNEE (best on BOTH on-correct and erroneous-time)**
- CONF=4: on-correct 63.4% / stale 23.4% / erroneous 13.1% / 32 FP / lat 13.3s
Going 3→4 cuts FP count 52→32 but buys ~ZERO erroneous-time (13.2→13.1; suppressed switches were brief) while adding 5.5pts stale/latency. So CONF=4 was strictly worse UX than 3. **SHIPPED: SWITCH_CONFIRM 4→3** (commit b22e5bb `[AUTOPILOT]`, supersedes 0a5c53f). Verified no regression on clean 3-shabad studio harness (pq_337→pq_3GL→pq_37N: 2/2 recall, 0 FP at CONF=3). This is the user's own predicted "middle ground 3." Harness UX metric lives in vf-kirtan-switch-eval.js (segAt/tStale/tErr).

**CUSUM negative result (2026-09-10):** added SWITCH_MODE=cusum to the harness (score-weighted accumulator on (contS-SMIN)+(margin-MARG), leak CDECAY, commit CTHRESH) to try for low-latency + low-FP without count's latency tax. **Real-app advantage the harness omits:** the shipped app requires SWITCH_CAND_MIN_VOTES=6 first-letter votes to even PROPOSE a candidate before the acoustic test. A spurious acoustic match to a short shabad usually won't also generate 6 first-letter votes for that shabad → the app's erroneous rate is likely BELOW the harness's 6.8%. Harness = conservative worst case.

**LENGTH-AWARE CANDIDATE PENALTY = FIRST REAL WIN PAST THE ERRONEOUS CEILING (2026-09-10).** Root cause of erroneous switches: partialRatio is ASYMMETRIC (rewards a SHORT line found as substring of a longer hyp) → a 1-line shabad scores ~1.0 on a fragment of unrelated audio, esp. with a large shabad field. Fix: scale each line's score by `min(1, lineLen/MINCHARS)` so short lines need a higher raw bar. Harness: env `LEN_MIN` in maxLineScore (vf-kirtan-switch-eval.js). Results at LEN_MIN=15 CONF=3 (correct/stale/erroneous/recall, baseline→LEN15): 86min-voiceA 68.9/17.8/13.2/85 → **69.9/19.5/10.5/86** (clear win) · voiceB-45s 73.5/.../15.0/48 → 73.4/.../14.5/48 (flat) · multi20-45s FULL 64.4/17.4/18.1/78 → **64.7/17.8/17.4/78** (small win; the cap-20 pilot showed a bigger -5.9 erroneous but the full-set gain is only -0.7 — early window had more short-shabad confusions) · stress-multi20 19.2/.../48.8 → 19.0/.../49.0 (neutral — latency-bound, not short-line). HONEST SIZE: small-but-consistent net positive, biggest on the PRIMARY 86-min stream; ZERO regression, NO recall loss anywhere. **PORTED TO APP** (VoiceFollow.jsx): `maxLineScore` gained optional `minLineChars` param; new const `SWITCH_CAND_MIN_LINE_CHARS = 15` applied ONLY to the candidate score at the sCand call site (line ~862) — current shabad (cursorLineScore) left untouched so it stays strong = even more targeted than the harness.
